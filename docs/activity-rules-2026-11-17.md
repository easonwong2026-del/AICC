# 成长活跃规则取证（PR #102，2026-11-17；2026-11-18 修订）

四个国内版账号的实测取证。目的：在写"成长活跃管理"之前，先用服务端数据回答
"签到到底算不算活跃"。

采集方式：`bash scripts/collect-activity-evidence.sh`（只读，四个 GET）。
落盘的是**判定所需字段的摘要**（`docs/evidence/activity-*.json`，每份 < 1KB）；
365 天逐日轨迹不落库，避免把长期个人使用轨迹写进仓库。

> 该脚本调用 `growth.rewards.evidence`，而这条 RPC 只在 **debug 构建**注册
> （`#[cfg(debug_assertions)]`）。用正式 Release 的 worker 跑会得到"未知方法"，
> 必须用 `cargo build` 出来的 debug 产物。

## 一、结论（四条）

1. **签到与活跃是两条独立计数。** 四个账号从 11-13 起每天签到有新记录（本地全是
   `already`），但三个账号今天的热力墙仍是 `score=0 / is_active=false`、连登 0 天。
2. **连登天数与活跃天数一致。** 唯一有连登的账号（卡里，11-17 是 17 天，11-18 是 18 天）
   恰好是最近 7 天每天都 `score > 0` 的那个；其余三个账号历史活跃天数分别是
   1 / 6 / 79 天，但都不连续，连登都是 0。
3. **可观测事实到此为止。** 上面两条是服务端返回的数据，不涉及"为什么"。至于
   "活跃由什么行为产生"——**只拿到国际站条款原文**（见 §七），国内站成长中心的
   规则原文本轮没有取到，因此不做"只能由桌面客户端产生"这类推断。
4. **AICC 不自动产生活跃。** 无论最终规则如何，脚本化刷活跃在已知条款里都属于
   取消资格情形；AICC 的落点是"只读判断 + 提醒 + 回查"。

## 三、接口事实（可以直接照着写代码）

### `/v2/activity/growth/heatmap`

| 字段 | 含义 | 注意 |
| --- | --- | --- |
| `data.today.date` | **服务端自己的"今天"** | 界面的"今天"必须用它，不能用本机日期 |
| `data.today.is_active` | 今天是否已点亮 | 唯一权威的活跃判定 |
| `data.today.score` | 今日热度分 | 0 与 `is_active=false` 同时出现 |
| `data.today.status_text` | 给用户看的一句话 | 未活跃时是"开始使用以点亮今日热力墙" |
| `data.cells[]` | 365 天 `{date, score, has_new_buddy}` | 只用来数"最近 N 天有几天有分" |
| `data.updated_at` | **服务端记录的最后更新时间** | **不能证明当天完成过真实任务**，也不能单独用来判定"统计延迟" |
| `data.range` | `{days, start_date, end_date}` | `end_date` 通常等于 `today.date` |

### `/v2/activity/growth/streak`

| 字段 | 含义 |
| --- | --- |
| `data.streak.days` | 当前连登天数 |
| `data.streak.next_tier` | `7d` / `14d` / `28d` / 空 |
| `data.streak.next_tier_remaining` | 距下一档还差几天，**服务端算好的** |
| `data.streak.month_total_days` | 本周期内累计活跃天数 |
| `data.streak.makeup_dates[]` | 已补签的日期 |
| `data.launch_date` | 账号首次进入成长中心的日子 |
| `data.timezone` | `Asia/Shanghai`，服务端日期用它 |
| `data.redemption_status.tier_{7,14,28}d_status` | `locked` / `claimable` / `claimed` / … |
| `data.makeup_cards.{balance,max}` | 补签卡余额与上限 |

## 四、两个"不要自己算"的地方

1. **`next_tier_remaining` 不等于 `next_tier - streak.days`。**
   实测 SAMSUNG 是 `streak.days=0` + `next_tier=7d` + `next_tier_remaining=6`，
   而同状态的 高亮/一锅端 是 7。服务端的计数口径比"连登天数"多一层（当天已计入周期，
   但还没点亮），本地减法会算出 7，与界面上的 6 打架。
   **界面只显示服务端给的数字**，不做减法。
2. **跨日边界以 `today.date` 为准。** 本机 02:43（CST）与服务端一致，但 00:00–08:00
   之间本机日期可能已经翻页而服务端还没结算。判断"今天的签到记录还在不在"
   要用签到记录的 `local_date == today.date`，不能用 `Date()` 减一天。

## 五、能判定什么、不能判定什么

| 现象 | 可观测依据 | 能下的结论 |
| --- | --- | --- |
| 授权缺失 / 失效 | `broker::resolve` 拿不到凭据，或接口 401 | 授权不可用 |
| 今日已签到（服务端确认） | 签到状态接口 `todayCheckedIn = true`，或本地当天记录成功 | 签到完成 |
| 今日未签到（服务端明说） | 签到状态接口 `todayCheckedIn = false` | 签到未完成 |
| 签到记录缺失 | 本地没有 `local_date == 服务端今天` 的行，且没有查服务端 | **不知道**，不等于没签到 |
| 今日未活跃 | `is_active = false` | 未活跃 |
| 统计延迟 | **只有服务端自相矛盾时才算**（`today.score > 0` 但 `is_active != true`） | 可能延迟，稍后回查 |
| `updated_at` 是今天 | 只是服务端更新时间 | **什么也不能证明** |
| 账号身份错误 | 只读接口都不回 `uid` | **区分不出来**，不声称能判定 |

身份错误这一条要诚实：`/heatmap` 和 `/streak` 都不回 `uid`。当前能做的只有
授权探测失败时判"授权不可用"；"本地签到天天成功、但 `month_total_days` 长期为 0"
这种反常组合只能作为人工排查线索。

## 六、CodeBuddy CLI / IDE 与成长活跃

**本阶段不再研究。** 架构决策（2026-11-18）：

- CodeBuddy CLI、IDE、WorkBuddy 客户端都要求对应账号登录；即使 CLI 能计入，
  四个账号仍要各自认证并各自真实使用，解决不了多账号管理的核心问题；
- 自动发无意义对话、模拟客户端事件有账号与活动资格风险；
- 投入产出比不高。

因此：**AICC 不把它作为活跃手段，也不在界面上声称支持。**
若将来官方给出明确支持的能力，再单独立项评估。

## 七、规则依据（国际站与国内站分开）

| 来源 | 原文要点 | 本轮状态 |
| --- | --- | --- |
| WorkBuddy 国际站活动条款（`workbuddy.ai/docs/zh/workbuddy/Subscription`） | 一个活动日内"通过 WorkBuddy 或 CodeBuddy 客户端发起至少一次有效 AI 对话或任务"视为活跃；网页端不计；脚本 / 外挂 / 插件 / 模拟器 / 接口调用刷取属取消资格 | **已取得原文** |
| 国内站成长中心规则（`codebuddy.cn` / `workbuddy.cn`） | — | **未取得规则原文**，只有接口实测 |

所以本文档的结论分成两类：

- **接口事实**：来自四个账号的真实响应，可直接用于实现；
- **规则推断**：没有。国际站条款只用来解释"为什么不做自动活跃"，不用来推断
  国内站的判定细节。

## 八、合规边界（写进代码注释的那一条）

国际站条款把"脚本、外挂、插件、模拟器、接口调用、批量注册刷取活跃或奖励"
列为取消资格情形；国内站条款原文本轮没有取到，本产品线口径不会更宽。

因此 AICC 的实现边界：

- 只读 `GET /heatmap`、`GET /streak`，以及**只读**签到状态查询；
- 不构造 `chat_request_send` 之类的行为事件，不模拟客户端，不批量发送对话；
- 用户要活跃，就在官方客户端里做一件真实的事；AICC 负责提醒和回查。

## 九、这一轮不做什么

- 不自动补签（补签卡要花，且属写操作，走 #101 的二次确认链路）；
- 不做"每天自动发一条对话"这种伪活跃；
- 不在总览页定时轮询：活跃状态每次启动读一次，之后靠手动刷新。
