# 四账号成长活跃管理（PR #103，2026-11-17；2026-11-18 修订）

在 #102 的取证结论上做的一层只读功能：**每天看一眼四个账号的真实状态**——
谁已活跃、谁只是签到了、谁连签到都没确认、谁授权出了问题。

不做「自动活跃」。理由见 `docs/activity-rules-2026-11-17.md`：脚本刷取在已知条款里
属于取消资格情形，AICC 不去踩这条线。

## 一、后端：`growth.activity.status`

| | |
| --- | --- |
| 方法 | `growth.activity.status` |
| 参数 | `accountIds?: string[]`（省略 = 所有国内版账号） |
| 请求 | `/heatmap`、`/streak`；**本地拿不出成功签到记录时**再加一次只读签到状态查询（最多 3 个 GET/账号） |
| 写操作 | 无。响应固定 `"readOnly": true` |
| 超时 | 客户端 60 秒（4 账号最多 12 个请求，账号之间串行） |

### 1. 今日签到：五种结论，六个来源

签到这一列**不许和活跃合并**，也不许把"本地没记录"当成"没签到"。

| `checkin.state` | `source` | 含义 | 界面 |
| --- | --- | --- | --- |
| `confirmed` | `local` | AICC 本地当天记录是 `success` / `already` | 已签（本地） |
| `confirmed` | `server` | 服务端签到接口的 `checkin_dates` 含服务端今天 | 已签（服务端） |
| `absent` | `server` | 服务端明确没签，且本地也没有记录 | 未签到 |
| `failed` | `local` | 本地当天尝试失败（服务端也没说签过） | 签到失败 |
| `unconfirmed` | `server`/`local`/`null` | 本地没记录且服务端状态取不到；或本地状态是 `unknown` / `disabled` | 未确认 |
| `auth_unavailable` | `null` | 授权不可用 | — |

判定顺序：

1. 没有服务端日期 → `unconfirmed`（不知道"今天"是哪天，任何记录都不能算）；
2. 本地成功类记录 → `confirmed(local)`；
3. 服务端说签过 → `confirmed(server)`，**可以覆盖本地的 failed**；
4. 本地失败类记录 → `failed`；
5. 服务端说没签 → `absent`；
6. 其余 → `unconfirmed`。

**为什么必须查服务端**：2026-11-18 02:43 实测四个账号，AICC 本地只有 11-17 的记录，
但服务端签到接口的 `checkin_dates[0]` 是 `2026-11-18`。按本地记录判断会得出
"今天签到没跑"，而事实是已经签了（AICC 只是没有那一行记录）。
`checkin_dates` 比 `today_checked_in` 更硬：它能把"服务端的今天"和"我们的今天"对齐。

> 上游把 `todayCheckedIn` 的缺省值写成了 `false`，所以解析时只认 `raw` 里**显式**
> 出现的 `today_checked_in` / `todayCheckedIn`；字段缺失一律视为"不知道"。

### 2. 诊断码：七种，动作各不相同

| code | 判定依据 | 界面短标 | 建议动作 | 提醒 |
| --- | --- | --- | --- | --- |
| `active` | `is_active = true` | 已活跃 | 不用处理 | 否 |
| `checkin_only` | 未活跃 + 签到确认 | 未活跃 | 去客户端做一次真实任务 | 是 |
| `checkin_unverified` | 未活跃 + 签到未确认 / 失败 | 签到待查 | 去签到页确认，或等下一次自动签到 | 是 |
| `inactive` | 未活跃 + 服务端明确没签到 | 今日未用 | 先补签到，再用客户端做一次真实任务 | 是 |
| `stale_stats` | 未活跃，但 `today.score > 0`（服务端自相矛盾） | 待落库 | 稍后刷新回查，别重复做事 | 否 |
| `unknown` | `/heatmap` 没读到 | 未知 | 刷新重试 | 否 |
| `needs_auth` | 凭据缺失 / 401 | 需授权 | 重新授权或同步账号 | 是 |

`updated_at` **不参与判定**。它只是服务端最后更新时间，不能证明当天完成过真实任务；
唯一能说"可能延迟"的证据是服务端自己矛盾：有分数却没标记活跃。

## 二、界面：总览页第二层

`ConsoleActivityBlock` 放在统计卡下面、服务平台上面。

| 列 | 内容 | 备注 |
| --- | --- | --- |
| 账号 | 昵称 + `近 7 天活跃 N 天 · 上次 MM-DD` | 延迟时第二行换成"今天有分数未落库，稍后回查" |
| 状态 | 四字短标签 | 完整 `label · action` 在 tooltip |
| 今日活跃 | `已活跃 · 105 分` / `未活跃` / `—` | 未知一定是 `—` |
| 今日签到 | `已签（本地）` / `已签（服务端）` / `未签到` / `签到失败` / `未确认` / `—` | tooltip 给证据链：服务端最近签到日、本地状态、为什么未确认 |
| 连登 | `连登 17 天` | 只来自 `/streak` |
| 下一档 | `28 天档 · 还差 11 天` | 服务端 `next_tier_remaining`，不做减法 |
| 右列 | `checkin_only` / `inactive` 给「打开客户端」；其余给短动作词（看签到 / 去授权 / 稍后刷新） | 不给按钮就不假装能一键解决 |

页脚：需要处理的账号逐条列出（昵称 + 建议动作），再补充延迟账号数量，最后一句固定
写明"签到只记账，不点亮热力墙；活跃要在客户端真实使用一次；AICC 不切换账号"。

### 为什么这一块没有"一键活跃"

- 活跃只能由客户端里的真实使用产生；AICC 能做的只有打开客户端；
- 「打开客户端」是 `NSWorkspace` 打开本机 `WorkBuddy.app`（找不到时按钮禁用并说明），
  **不切换账号**：仓库没有账号切换能力（`docs/UI_CONSOLE_V3.md` §账号切换永久关闭）；
- 打开总览时自动读一次（每次启动仅一次），之后只靠「刷新」，不定时轮询。

## 六、这一层不做什么

- 不发任何 POST，不伪造行为事件；
- 不自动补签（有成本且有写操作，走 #101 的二次确认链路）；
- 不做"每天自动发一条对话"的伪活跃；
- 不把读取失败、签到未确认算成"未完成"去催人。
